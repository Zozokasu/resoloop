# Resonite Flux

Flux deployment participates in the ResoniteLink URL writer lock used by apply, direct edits, capture and probes. Each deployment holds the lock through readback and Flux deploy-state commit. `APPLY_SESSION_BUSY` means another cooperating writer currently holds it. The lock coordinates ResoLoop writers on this PC and OS user; it does not make a world batch atomic or exclude external and unobserved writers. For changes to world declarations/binding targets, preserve v3 apply state and follow [apply recovery](../resonite-build/references/apply-recovery.md) before further deployment. Apply `propertyModes` runtime/driver-owned values are not written by ordinary apply, but declarations do not prove actual driver ownership. Old-driver replacement uses the staged workflow in that reference.

Keep ProtoFlux logic in .pg files. Confirm `resoloop flux status --json`, the active ResoniteLink URL, and that `resoloop doctor --json` reports a successful managed-data check/build probe through either the configured path or Flux-SDK auto-discovery.

Start with Reflection and bounded observation: run `flux status --json` and `doctor --json`, then use `find`/`inspect` to identify the exact destination parent and relevant bindings. Keep observations bounded to that parent and its direct children. Never target Root. Run `flux check` for fast semantic diagnostics, then `flux build`; fix `primaryDiagnostics` first and note their stdout/stderr source and parse/type/cascade category. For deployment, the deployer compiles again and treats its error diagnostics as authoritative: errors stop before any send, warnings are reported and may continue. The execution compile must still match the preparation compile for module name, port shape/types, and binding maps. Same-shape graph-body changes may pass; this is not an exact source-byte binding check. Validated source port declarations (name, direction, type, and modifier) must agree with recognized generated carrier evidence during preparation. Unknown or unsupported bound carrier/modifier evidence, including mutable ports, can fail with `FLUX_BINDING_PORTS_MISMATCH` before lock, pending state, or execution; not every valid Flux-SDK port form is necessarily supported. This check does not make unavailable target-type/interface evidence a failure. Manifest deployment also checks exact-version runtime compatibility before mutation. `FLUX_RUNTIME_NODE_INCOMPATIBLE` means the source built on that pair but is known to fail when Resonite loads the record; use the reported bounded workaround. Do not generalize the quarantine to unobserved versions.

Before deploy, verify that the module's declared `in` and `out` names match the manifest binding keys and modes: inputs use `mode: source`, outputs use `mode: drive`. Every manifest port must be bound. A wrong or unknown key, wrong mode, or unbound manifest port fails before deployment. If bindings exist but preparation cannot report compiled ports, deploy stops before mutation because keys cannot be checked. A single-module deploy with no bindings may proceed with unknown ports reported as a warning. Flux scalar aliases such as `int`/`int32`/`System.Int32` and `bool`/`System.Boolean` compare as the same type. Inspect the reported `bindingTypes` and port verdict; a matching scalar type alone does not prove the binding target is correct.

Pass an explicit non-Root parent (`--parent` or manifest `parent`). Single deploy stores its checkpoint under `<project>/.resoloop/flux-state/deploy/<safe-module-path>.json`; manifest `deployState` is the deployment checkpoint, while `worldState` resolves stable binding selectors. CLI `--state` paths are relative to the current directory; manifest paths are relative to the manifest. Flux state v2 records `kind`, normalized URL plus matched `S-` ID, module parent/root IDs, declared name, input hash, and pending operations. v1 is migrated on save; `origin: migrated-v1` marks a legacy ID as unverified until that exact Slot is freshly observed under the same parent with the compiled declaration name. The migrated origin remains through a not-sent or failed replacement; it becomes `deployed` only after successful deployment readback. For guard/no-op ownership checks, normal deployed IDs require cached guard evidence with the stored normalized URL and matched, non-null `S-` ID; this evidence is not refreshed by each observation. The actual writer uses its own fresh URL-announcement window, with versions observed separately from that writer connection session data. Unknown cached guard identity cannot authorize an old deployed ID or a no-op that depends on it. Missing fresh writer announcement evidence is reported unknown, but does not by itself block an otherwise authorized new or replacement deployment or normal readback settlement of that in-flight operation; it supplies no new ownership proof. A known mismatch refuses before writes or keeps the sent operation pending. A Flux pending operation interrupted by an earlier run is never auto-settled and requires separate recovery. `S-` is not a WebSocket connection-bound ID. A confirmed session-epoch change invalidates prior deployed ownership records; any surviving same-name child then stops as unrecorded. Never infer announcement identity from `UniqueSessionId` or runtime session data. Older CLIs reject v2 state.

Every deploy verifies the direct children under the parent before sending, replacing only the recorded old root whose name matches the compiled module declaration. Untracked same-name children are a hard stop; do not delete or adopt them by name. After deployment, inspect the exact returned module root and its binding targets. A readable mismatch fails; unreadable evidence remains unknown and pending. On failure, read the operation ID and candidate root IDs from diagnostics. A pending deployment blocks the next run, and watch stops on pending state or `APPLY_SESSION_BUSY` without retrying. Inspect those exact candidates and parent in the live world first, then discard only the selected operation offline:

```powershell
resoloop flux deploy --project PROJECT --module MODULE_PATH --discard-pending OPERATION_ID --yes
resoloop flux deploy-manifest MANIFEST.json --discard-pending OPERATION_ID --yes
```

This removes one pending record and writes nothing to the world; `--yes` is required and an unknown operation ID is rejected. A discarded candidate is never adopted automatically and may remain in the world. If a candidate ID is unknown or absent, the created root may be impossible to distinguish and a later deployment can create a duplicate. Re-inspect exact IDs after any deployment or recovery action.

Discover exact node identities and ports with `resoloop flux node search` and `resoloop flux node describe`; do not infer a node from its short name. The catalog preserves duplicate short names by full runtime identity and is cached by Flux-SDK/library identity. A successful build that packs zero nodes is not deployable: keep a reachable entrypoint such as CallInput, LocalUpdate, a Dynamic Impulse receiver, or another graph consumer.

Design every graph with an explicit processing user and state scope. ProtoFlux impulses execute locally, but by default their mutations of the FrooxEngine data model—such as writes to non-driven synchronized fields, Slot or Component changes, and non-driven DynamicVariables—are synchronized to the session. Treat a data-model value as shared unless the exact type/member is verified as local or non-synchronized. Identify who owns every entry impulse: `LocalUpdate` fires once per user on that user's update, `LocalUser` is the user executing the current context, and user inputs on update/listener/event nodes must not be left ambiguous. Do not let per-user entrypoints write the same synchronized state unless multiple writers and their conflict behavior are intentional. For authoritative shared state, choose one writer, gate before the mutation, and make the authority policy explicit; the host is a common policy, not a universal default, and a headless session may be the host. Keep per-user input, presentation, prediction, and other client-only behavior local.

Choose storage by both lifetime and visibility: `Local` lasts only for one impulse context; `Store` persists across contexts but has a separate non-networked value for each user; `Data Model Store` and ordinary non-driven synchronized data-model fields are shared and synchronize when written; `Drive` continuously evaluates a target locally and is not a synonym for network synchronization. The manifest binding `mode: drive` only connects a module output to a member and does not change these multiplayer rules. Avoid synchronizing transient every-update values when a local calculation, per-user `Store`, event/intent sent once to an authoritative writer, or lower-frequency state transition is sufficient. For Dynamic Impulses, make the target hierarchy, receiver tag, originating/processing user, and intended local-versus-shared effects explicit. Verify multiplayer-sensitive graphs with at least two users or clearly report that only single-user structural behavior was checked.

For multiple modules or hot reload, keep a checked-in schema-v1 Flux module manifest with explicit `dependsOn`. Run `resoloop flux validate-manifest MANIFEST.json --json` before connecting or deploying. Prefer a `$slot:key` parent plus the matching world apply state; resoloop verifies a same-connection ID or resolves the saved path after reconnect. Declare every module `in`/`out` in `bindings`: use `mode: source` for an `in` name targeting `$slot:key`, `$component:key`, or `$member:key.Member`, and `mode: drive` for an `out` name targeting `$member:key.Member`. Never paste session-scoped IDs into a manifest. A command-line `--state` path is relative to the current directory; `worldState`, `source`, and `deployState` inside the manifest are relative to the manifest. Treat unbound ports, direction/type mismatch, and unresolved bindings as pre-deploy failures. Run `flux deploy-manifest` once, then use `flux watch MANIFEST.json` in the foreground. It topologically builds changed modules and deploys only successful builds. Preserve its deploy-state checkpoint and follow the non-atomic recovery report after failure.

For a bounded pool of interchangeable bullets, targets, effects, or enemies, deploy one controller module for the pool rather than one full graph per instance. Keep template-local Flux limited to unavoidable drivers or local adapters. Store instance state in consistently typed, namespaced DynamicVariables such as `Projectile/Active`, `Projectile/Velocity`, and `Projectile/Chain`; have the controller traverse the pool, claim inactive entries, update them, and reset all state before reuse. Keep allocation bounded and define exhaustion behavior. This prevents ProtoFlux node count and deploy cost from scaling with the number of pooled instances.

After deployment, use `parentSlotId` as the destination, `moduleSlotIdBefore` as the old root recorded in state and trusted for this run, and `moduleSlotIdAfter` as the root ID returned by the deployer and verified by readback. Re-inspect that exact child and each generated input/output reference target. Put the module below the Grabbable root when it must travel with an item, and confirm with `resoloop item audit ROOT --strict`. Stop watch on cancellation. Do not reimplement compilation or generate ProtoFlux nodes directly—use Flux-SDK. Treat an untested Flux-SDK series reported by doctor as a compatibility warning that must be resolved before live deployment. Flux-SDK 1.9.x interface globals such as `IButton global` are rejected before deploy; prefer a concrete Component `element` input and convert it inside the module with `asDrivenGlobal`, or use a Dynamic Impulse bridge for event-only coupling. ResoniteLink 0.13.1 cannot itself fire that bridge, so runtime verification still needs an in-world producer.
