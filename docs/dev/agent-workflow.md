# エージェント体制と実行プロトコル

方針版: `2026-10-02-delegation-v2`。通常の開発と`/ccg:go`に適用する。2026-10-01の「6.1-sol一担当が調査・実装・検証を通す」方針を置き換える。役割の正本はこの文書、アーキテクチャとResonite安全規則の正本は`AGENTS.md`とする。

**具体的な構成以上に、厳格な運用方針とその枠の中での柔軟さの確保を重視する。** 目的、共有契約、アクセス権、編集の所有、検証、受け入れ責任を固定し、その内側で担当モデル・effort・分割・参照情報・並列数を調整する。

ccgの戦略・モデル解決・正規起動・task lifecycleとHARD STOPゲートは維持する。実行モード選択はユーザー決定済みの本体制を宣言し、毎回選択を尋ねない。hookは短い規則とこの正本への参照を注入する。指示が矛盾したら版と権限を確認し、旧体制と混ぜて起動しない。

## 役割は三層、通常の実行は二層

| 役割 | 担当 | 責任 |
| --- | --- | --- |
| オーケストレータ | Opus 5.5 high | 目標、優先順位、機能間の共有契約、付与権限、節目の受け入れ、merge判断、担当間の衝突、liveの許可と対象 |
| 技術マネージャ | Codex `gpt-6.1-sol` high | 調査・分割・タスク契約・委任・情報補充・差分確認・統合検証・進行記録。通常の修正ループを完結させる |
| 実装担当 | Codex `gpt-6-luna` high | 許可された範囲の実装とそのtest、局所検証、短い報告 |
| 実行・集計担当 | Codex `gpt-6-luna` | ログの取得、build／testの実行、結果の要約 |
| 調査・検証・重点レビュー担当 | 必要な場合のみ | 情報探索、許可された実機検証、実装担当と別文脈での高影響の確認 |

マネージャ規則は`.claude/agents/feature-manager.md`、実装担当規則は`.claude/agents/coding-worker.md`。ClaudeのSonnet feature-managerは管理役の予備であり、実装へ戻す抜け道にしない。Devin SWE-2 Maxは利用可能な環境での任意の実装担当として残す。

Opusとマネージャは製品コードを書かない。マネージャは担当の出力を機械的に適用できるが、修正と製品コードの競合解消は実装タスクとして渡す。難しい変更では、タスクを小さく分け、契約へ渡す情報を増やす。管理役が実装を引き取らない。メタ設定の変更と製品実装を区別する。モデルの割り当てと契約の書き方は、末尾の「Codexのモデルの使い分け（2026-10-08）」に従う。

通常の情報補充・テスト失敗・担当交代はマネージャが扱い、Opusへは契約を満たした変更群と例外をまとめて報告する。起動をOpus側から中継する場合も、付与済み権限内の各修正に新たな判断を要求しない。

## 固定する規則と調整できること

| 項目 | 固定する規則 | マネージャの調整権限 |
| --- | --- | --- |
| 目的・完了 | 合意した挙動、互換性、受け入れ条件を維持 | 順序と担当、内部実装の選択 |
| 共有契約 | Core公開型、`IResoniteClient`、CLI、公開JSON、エラーコード、state、依存方向の変更はOpusが確定 | 確定した契約内での分割と実装方式 |
| 権限 | read/write・ツール・ネットワーク・live・Git操作を分けて付与 | 付与済み範囲内で子へ渡す情報と編集対象を拡縮 |
| 所有 | 同一ファイルの編集・適用は同時に1担当。変更元が古い出力を適用しない | 所有解放後の担当交代と統合順序 |
| 品質 | リスク別の検証、差分確認、必要な重点レビュー | 検証の追加、情報補充、モデル・effortの変更 |
| 記録 | 未検証を明示。実効モデル、契約版、差分、検証証拠を記録 | ログ要約、時間配分、許可された上限内の並列数 |

目的・受け入れ条件・付与権限の変更は付与元へ返し、改訂理由を記録する。子の情報不足は必要な型・呼び出し元・テストを補って解決する。情報量を減らすために必要な文脈を削らない。

## タスク契約と文脈の渡し方

Opusはマネージャへ、目的・付与範囲・共有契約・受け入れ・live/Git権限・作業場所・予算を渡す。マネージャは子ごとに、task ID、契約版、リスク、独立した目的、read/write範囲、依存と所有、変更元commitと未commitファイルhash、検証コマンド、受け入れ条件、時間・試行上限、出力形式、ログと報告先を記録する。

子の新規起動には自己完結したタスク文を渡し、不要な会話履歴を継承させない。履歴制御APIがある場合は最小限の継承を選ぶ。このチャットの`fork_turns="none"`を、別のCLIにもあると推測しない。修正は既存担当へ返してよい。交代時は契約・差分・既存証拠・未決事項だけを引き継ぐ。

| 実装方式 | 適する変更 | 渡す情報と適用条件 |
| --- | --- | --- |
| メソッドの置換出力 | 依存を特定できる局所修正 | 対象メソッド全体、必要な型・定数・補助関数、呼び出し側の期待、境界テスト。署名とhashを照合し、対象外差分を拒否する |
| ファイル・機能単位 | 新規実装、非同期処理、状態遷移、複数ファイル | 必要な参照ファイルと許可された編集対象、契約、既存テスト。公開型や生成物の変更は個別に許可する |

挙動変更のテストやCLI変更時のREADME・製品Skill同期も、許可対象または依存タスクとして確保する。担当の出力に合わせて受け入れ条件を緩めない。生成物はAGENTS.mdのContractGen規則に従う。

## 制限の希望と実効アクセスを区別する

read/write範囲を指示すること、差分を検査すること、閲覧を実際に拒否することは別である。タスク契約に閲覧制限の要否と実効方式を明記する。worktree、作業ディレクトリ、`workspace-write`、履歴非継承だけでは限定閲覧を保証しない。

- 指示と差分検査だけの通常担当は「閲覧制限の強制なし」と記録する。厳密な限定閲覧が要件のタスクをこの方式で起動しない。
- 厳密な方式は、repoにアクセスするツールを渡さない断片呼び出し、または必要なファイルだけを提供する独立環境とする。未対応なら起動を止め、対応可能な方式へ切り替える。
- 許可外の情報が必要なら子は範囲外を読まずに要求する。マネージャは付与済み範囲で補充し、その外の権限はOpusへ返す。
- 隔離環境と専用実行器は、許可外read/write、パス遡り、symlink/junction、古いhash、並行適用を拒否する試験が通るまで保証済みと扱わない。この体制変更は専用実行器や隔離機構を実装したことを意味しない。

適用は排他の下で変更元を再確認し、未commitのユーザー変更を保護する。複数ファイルは候補ツリーへ適用し、途中状態を統合済みとしない。パス検査だけでAPIの意味や互換性を保証しない。build/testもコードを実行するため、固定コマンドは隔離の代わりにならない。

## リスク別の検証と受け入れ

| リスク | 例 | 必須の確認 |
| --- | --- | --- |
| 局所 | 明確な変換、引数検証、内部ヘルパー | 関連build/test、マネージャの差分確認 |
| 機能内 | 複数ファイルの機能追加、adapter内の変更 | 関連build/test、影響先の統合検証、契約確認 |
| 高影響 | state、所有権、削除、接続世代、並行性、公開JSON/CLI/エラーコード、C#とTSの契約 | 必要な共有契約の事前確定、マネージャによる設計と小さく分けた契約、統合前の独立した重点レビュー（`gpt-6.1-sol` high）、影響先の検証 |

行数で分類せず、影響が広いと判明したら引き上げる。重点レビューは別文脈で要件・契約・差分・証拠を読む。実装担当の説明だけで判定しない。同じモデルの別セッションでもよい。局所修正のたびに独立レビューを必須にしない。

担当の`DONE`や終了コードは完了の主張である。受け入れには契約版、正確な差分、範囲適合、検証結果、未検証事項が必要。候補ツリーへの適用後に統合検証を行う。通常は事前restore済みの`dotnet build ResoLoop.slnx --no-restore`と、影響先の`dotnet test ... --no-build`を使い、共通基盤の変更では全体へ広げる。

検証再利用はcommit・未commit差分hash・依存・環境・コマンド・test集合の一致が条件。liveはセッション世代と観測した状態も条件に含める。環境変化や不確かな結果があれば再検証する。pass/fail/skipと未検証を分け、全文ログはcharter指定先、報告は10行程度の要約にする。

フェーズ末に全差分（開始commit..対象commit）の重めのCodexレビューを1回行う。重点レビュー済みの証拠は引き継ぎ、統合後の相互作用と未確認領域を優先する。対象hashとレビュー後の変更を区別する。レビュー後の修正ラウンドはユーザー判断を維持する。既に明示されたフィードバック修正の範囲は再承認を求めない。重大な設計変更のみ再レビューする。

## 所有・並列・追跡・例外

実装担当1〜2人から始める。契約・依存・ファイル所有が独立し、実測で効果がある場合に3人まで増やす。共有型、CLI引数、README、製品Skillの所有は一人に決める。1作業ツリーのbuild担当は一人、liveは一件とする。同じ作業を重複起動しない。

並列作業には既存の`scripts/agents/new-worktree.ps1 -Name <task> -Slot <1-3>`を使う。本体ツリーの使用はcharterで指定する。commitは許可された`agent/*`ブランチのみ、mainへのmergeはユーザー承認後に`--no-ff`。依頼のないcommit/push/releaseはしない。sandboxからGit管理領域へ書けなければ権限を迂回せず、未commit差分とcommit案を返し、許可された担当が適用する。

追跡は既存の`.ccg/tasks/<task>/assignments.md`に集約し、マネージャか実行担当が更新する。並列の子は直接更新しない。既存の`planned / running / review / integrated / blocked / failed`を維持し、契約の準備・検証中・受け入れ候補を証拠欄で区別する。統合先とcommitを記録し、候補への統合とmainへのmergeを区別する。ccg managedファイルのschemaは変更しない。

同じ原因で2回失敗したら、情報補充・分割・モデル・方式を見直す。上限を未指定のまま無制限に実行しない。期限や予算到達時は成果と証拠を保存し再計画する。担当交代前に元担当を停止し、所有を解放する。

| 事象 | 判断先 |
| --- | --- |
| 付与済み範囲の情報補充・子の編集範囲変更、検証失敗、モデル交代 | マネージャ。契約版と理由を更新し、必要な検証を追加 |
| 付与権限外のアクセス、共有契約変更、担当間の衝突 | Opus。論点・選択肢・推奨・影響をまとめる |
| 目的・許容範囲変更、未承認のlive/merge、受け入れ条件の緩和 | 既存workflowの権限者。必要な場合にユーザーへ確認 |

## 起動と利用可能な能力

既存のマネージャ起動形（codex-cli 0.159.2のhelpと従来記録を確認）を維持し、charterに管理専任と本規則への参照を書く。

```bash
codex exec --model gpt-6.1-sol -c model_reasoning_effort=high --sandbox workspace-write -C "<worktree slot>" -o "<報告ファイル>" - < "<charter.md>" &
```

charterはファイルから標準入力で渡す。Windowsの改行入り引数は従来記録で問題がある。effortは`-c model_reasoning_effort=...`で指定する。共通設定だけで実効値を判断しない。

試験開始時に、子の起動・モデル指定・結果回収・停止・実効権限を小さな委任で確認する。nativeの子起動が使えればマネージャが委任する。使えなければマネージャが`NEEDS_DISPATCH`として自己完結した子タスク契約を返し、Opus側の既存実行手段が中継する。自動中継があると推測せず、確認できた経路を記録する。委任不能のときは管理役の製品実装で代替しない。

従来記録ではsandbox内のネットワークとworktreeのGit書き込みに制限がある。NuGet restore/npm ciは許可された外側の担当が事前に行い、内部で無断restoreしない。live担当は接続可能で許可された環境を使い、sandbox迂回の危険なフラグを追加しない。

Devinを使う場合はsandbox外で、信頼済みの担当slot、自己完結したprompt file、`.devin/config.local.json`で許可された完全一致コマンドを使う。任意の外部起動や閲覧を推測しない。信頼設定を編集せず、`--permission-mode dangerous`は使わない。未信頼なら別の実装担当へ渡す。起動例は`devin --model swe-2-max --permission-mode accept-edits -p --prompt-file "<指示ファイル>"`。その制限の実効性も実行環境で確認する。

## S3実機テストとフィードバック修正で試験する

ユーザーからS3実装完了の報告を受けた。完了した実装と実機で確認済みの挙動を分け、以下を新体制の最初の試験手順とする。指示ファイルの切り替え自体はliveの実行許可ではない。

1. マネージャがS3の対象commit/未commit差分、既存offline証拠、未検証事項を確認し、開始時点を記録する。実装を最初からやり直さない。
2. Opusがユーザーの実行許可と正確な対象を確認し、マネージャへlive charterを渡す。セッション、接続先、`ResoLoop_Test*` Slot、許可操作、cleanup、再接続時の再観測を記録する。
3. マネージャが検証担当を一人指定する。`AGENTS.md`のopt-in（`RESOLOOP_RUN_INTEGRATION=1`、`RESONITE_LINK_URL`、`Category=Integration`）と許可済みのシナリオを使う。ライブ用排他ラッパーは未整備なので、Opusが使用を調整し、正確な実験Slotだけをfinallyで片付ける。
4. 指摘ごとにID、期待/実際、再現手順、対象差分、セッションとSlot、ログ・観測証拠を記録する。環境・前提・製品バグを切り分け、既存feedbackの指定先を使う。正式planは書き換えない。
5. マネージャが修正をリスク分類し、実装担当へ委任する。範囲内の局所修正は通常二層で進め、共有契約変更はOpusへ返す。関連offline検証と必要な重点レビューを行う。
6. 実機再検証は、実行許可が覆う同じ対象・操作・範囲で行う。対象や操作が広がれば付与元へ返す。シナリオの期待結果とcleanup結果を別に記録する。実行できなかった項目は未検証のまま残す。
7. 指摘IDごとの修正差分・offline/live結果・未決事項と、委任待ち時間・修正回数・モデル費用など取得できた運用指標をまとめ、OpusがS3の受け入れを判断する。

S3試験中は、通常の局所修正がOpusの再判断なしで進むこと、範囲拡張が正しい担当へ戻ること、検証証拠が受け入れまで維持されることを観察する。速度向上を理由に権限や検証を省略しない。実効隔離や自動中継が未整備なら、その限界を報告する。

## 開発方針の前提

通常制作は直結: TSX/JSON/ProtoGraph → ResoLoop → RLoop.ResoniteLink（選択した単一セッション）、またはRLoop.Flux → IFluxDeployer → F# deployer → Flux-SDK。Workbench backend（`src/RLoop.Workbench`、`--backend workbench`、`wb`）は凍結し、新機能・書込みadapter・backend同等化・自動fallbackへ投資しない。既存planのS1〜S5に従い、old W4を再開しない。

`.ccg/`のmanaged領域、`plan/`、信頼設定を無断変更しない。既存ユーザー変更と未追跡ファイルを保持する。製品の`skills/codex/*`を開発担当の指示へ転用しない。

## 決定論的な検証を自動化する（2026-10-05）

build、テスト実行、件数集計、差分・hash照合、merge前のGit状態確認だけを行うために、追加のエージェントを起動しない。マネージャが `pwsh -File scripts/agents/verify.ps1 -Profile All` を直接実行する。影響が限られる場合は `Dotnet`、`Jsx`、`JsxContract`、状態確認だけなら `Inspect` を選ぶ。使い方と対象範囲は [定型検証の手順](deterministic-verification.md) にまとめる。

全文ログはファイルへ保存し、通常は `summary.json` と10行以内の実行結果だけを読む。失敗時は該当stepのログを調べ、修正が必要になった時点で実装担当へ渡す。成功したstepを理由なく繰り返さず、全体検証は最終候補にまとめる。TSのコンパイルを含む実行では、別のtypecheckを重ねない。

製品コードの修正、原因の判断、設計、必要な独立レビュー、受け入れは既存の担当方針を維持する。このrunnerはoffline専用で、実機実行・merge・push・ブランチ削除は行わない。liveの許可と安全規則、検証再利用の一致条件も変えない。

## Codexのモデルの使い分け（2026-10-08）

2026-10-08のユーザー決定。役割・権限・検証の規則は変えず、Codexのモデルの割り当てと、契約の書き方を定める。

| 作業 | モデルとeffort |
| --- | --- |
| 設計、分割、タスク契約、差分確認、重点レビュー、受け入れ候補の判断 | マネージャ `gpt-6.1-sol` high |
| 製品コード・test・文書の実装と修正 | `gpt-6-luna` high |
| ログの取得、build／testの実行、結果の要約 | `gpt-6-luna`（既定はmedium） |

- マネージャは全文ログを読んで集計しない。実行・集計担当へコマンドと出力先を渡し、10行以内の要約（件数、失敗したtest名、該当ログの path:行番号）を受け取る。失敗の原因の判断はマネージャが行う。`scripts/agents/verify.ps1` が使える環境では、その実行もこの担当へ渡してよい。
- 実装担当のモデルを上げて難しさを解決しない。同じ原因で2回失敗したら、分割と渡す情報を見直す。それでも進まなければOpusへ返す。モデルを変えるかはユーザーが決める。

### lunaへ渡す契約は短く明確に書く

`gpt-6-luna` は大きな推論を前提にできない。設計と判断を契約の前に済ませ、担当には明確な手順を渡す。

- 1契約は1目的にする。編集するファイルは少数（目安は3つまで）にし、正確なパスで挙げる。
- 名前、signature、エラーコード、期待値は、マネージャが決めて契約に書く。担当に設計の選択や広い探索を任せない。必要な型・呼び出し元・似た既存実装は、path:行番号か抜粋で渡す。
- 手順は番号付きにし、各手順の後で実行するコマンドと成功の条件を書く。
- 入力と期待する出力の具体例を書く（通る例と、拒否される例）。
- 禁止事項は、そのタスクで起こりうるものだけを短く書く。
- 本文は短くする（目安は60行以内）。経緯や、他のタスクの事情を入れない。
- 契約が長くなる、または手順が8つを超えるなら、タスクを分ける。

### 実装にはtestを含め、testのファイルを大きくしすぎない

- 実装のタスクは、その挙動を確かめるtestの追加・更新を同じ契約に含める。担当が実行し、結果を報告する。期待値は契約に書いた値から作り、実装の出力から作らない。
- testは機能や単位ごとにファイルを分ける。新しいtestのファイルは300行以内を目安にする。既に500行を超えるファイルへは足さず、新しいファイルを作る。既存の大きいファイルの分割は、頼まれた場合だけ行う。
- 1つのtestは1つの挙動を確かめる。共有する準備は小さなhelperにまとめる。
