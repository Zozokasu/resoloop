# エージェント体制と実行プロトコル

`/ccg:go`を含む通常の開発で使う役割分担。
`/ccg:go`実行時は、プロジェクトhook（`scripts/agents/ccg-go-roles.mjs`）がこの文書の要点を注入する。
ccgの戦略・モデル解決・タスク作成（`.ccg/tasks/<task>/task.json`）はccg-workflowの手順をそのまま使い、この文書は「誰がどの判断と作業をするか」だけを上書きする。

ccgの戦略にある「実行モードの選択」（Agent Teams / Codex / Claude）は、このプロジェクトではユーザーの常設承認により「feature-manager（Sonnet）＋Devin SWE-2 Max、大規模レビュー・資料はCodex」に固定する。Opusは選択肢を尋ねずにこのモードを宣言する。
それ以外のHARD STOPゲートは、戦略の定義どおりに残す。

アーキテクチャ、Resonite安全規則、上流の扱いは`AGENTS.md`を正とし、この文書では繰り返さない。

## 役割と決定権

| 役割 | 実体 | 担当 | 決めてよいこと |
| --- | --- | --- | --- |
| プロデューサ・議長 | メインセッション（Opus） | 目標・優先順位・受け入れ条件・機能間契約、マネージャの設置と担当範囲の承認、衝突解決、live検証の実行可否 | マネージャの設置・権限付与、契約の確定。ユーザーの目的や許容範囲を変える判断だけはユーザーに聞く |
| 機能マネージャ | `feature-manager`エージェント（Sonnet） | 担当機能の仕様理解・設計、SWE-2タスクへの分解、指示ファイル作成、SWE-2の起動・回答・受け入れ、統合と担当範囲の検証 | 承認された範囲内の局所的・可逆的な判断 |
| 実装担当 | Devin SWE-2 Max（`--model swe-2-max`） | 指定された編集範囲の調査・実装・関連テスト・局所検証 | 編集範囲内の実装判断 |
| 大規模レビュー・資料 | Codex（`smart-friend`スキル、またはccgの`codeagent-wrapper --backend codex`） | 機能横断レビュー、設計資料・引き継ぎ資料 | なし（指摘と資料を返す） |

- Opusはファイル単位の実装・修正と、マネージャと重複する詳細調査・タスク分解をしない。マネージャへの依頼（charter）は目的・範囲・契約・受け入れ条件だけにする。
- Opus自身の調べものは`scout`サブエージェントに委譲し、`path:line`と要点だけを受け取る。
- Codexは小さな変更の必須承認者にしない。レビューは対象のcommitか差分を明示し、レビュー後の変更と混同しない。

## 通信とエスカレーション

- Opus → マネージャ: `Agent`（`subagent_type: "feature-manager"`。使えない場合は`general-purpose`に`model: "sonnet"`を付け、`.claude/agents/feature-manager.md`を読ませる）。
- マネージャ → Opus: 最終報告、または途中の`ESCALATE`報告。マネージャは他のマネージャを直接起動できないので、マネージャ間の調整はOpusが中継する。
- マネージャ → SWE-2: 下記の指示ファイル方式で起動し、追加指示は同じセッションへ`--resume`で送る。SWE-2の`NEEDS_INPUT`には、マネージャが既存の契約から答える。
- `ESCALATE`の条件: 他機能の契約変更、層の依存方向や責務境界の変更、要件解釈が大きく分かれる、マネージャ同士で合意できない。報告には「論点・選択肢・推奨と理由・影響する担当」を書く。

## Devinへの依頼と受け入れ

マネージャはタスクごとにUTF-8の指示ファイルを一時領域へ作り、Devinを担当ツリーで起動する。Claudeとの会話はDevinへ自動共有されないため、指示ファイルだけで作業できるようにする。指示ファイルはcommitしない。

```text
devin --model swe-2-max --permission-mode accept-edits -p --prompt-file "<指示ファイルの絶対パス>"
devin list --format json
devin --resume "<session-id>" --model swe-2-max --permission-mode accept-edits -p --prompt-file "<追加指示ファイルの絶対パス>"
```

指示ファイルには、実装担当という役割、目的、編集範囲、既存の型・API契約、受け入れ条件、変更してはいけない事項、許可済みの検証コマンド、既存ユーザー変更を保持する指示、commit/push/releaseの可否を明記する。報告の先頭は`DONE` / `NEEDS_INPUT` / `BLOCKED`のいずれかとし、変更内容、検証結果、未解決事項を返す。判断が必要なら安全に進められる範囲で止め、質問・選択肢・推奨案をまとめる。

同じタスクを重複起動しない。`NEEDS_INPUT`には既存の契約から回答して同じセッションを再開し、ユーザーの目標や許容範囲に関わる判断だけをエスカレーションする。完了報告や終了コードだけで受け入れず、差分と検証結果を確認する。

## 並列作業のルール

- 1ファイルの編集者は同時に1人。共有型（`RLoop.Core`の公開モデル）、`IResoniteClient`、CLIの引数定義、`skills/codex/*`、`README*`には所有者を1人決める。
- 機能間の契約が要るタスクは、契約をOpusが確定してから並列化する。契約を変えたら影響する担当に通知する。
- 作業途中のファイルを前提にして、別の担当が完了と判断しない。
- 同じ作業ツリーでビルドするSWE-2は、マネージャをまたいでも1人まで。本体の作業ツリーを誰に使わせるかはOpusがcharterで指定する。それ以外の並列SWE-2は、`scripts/agents/new-worktree.ps1 -Name <task> -Slot <1-3>`で固定のworktreeスロット（`..\resoloop-worktrees\slotN`）を使い、担当マネージャが統合（merge）責任を持つ。Devinは初めてのディレクトリを非対話では実行しないため、各スロットはユーザーが一度だけ対話的に信頼する（`cd ..\resoloop-worktrees\slotN`、`devin`、信頼を承認して終了）。Devinの信頼設定ファイルは編集しない。未信頼のスロットしかなければ、本体ツリーで順番に実行する。
- 並列数の目安: SWE-2は同時に最大3。ビルドは1つあたりCPUを数コア使うので、4以上に増やすときは実測してから。

## マネージャの文脈を小さく保つ

- マネージャはcharter 1件で終える。レビューの修正ラウンドや追加の依頼は、同じマネージャを`SendMessage`で延命させず、新しいマネージャに渡す。前のラウンドの状態は、追跡表・`review*.md`でファイルとして引き継ぐ。
- マネージャは自分で実装しない。例外は、統合時の数行の接着修正（目安10行未満）だけ。詳細なコード調査、実装、実機での試行錯誤はSWE-2に渡す。
- charterは、担当範囲を1〜3個のSWE-2タスクに分けられる大きさにする。越える場合は、Opusがマネージャを分ける。
- Opusは、マネージャの報告の長さとツール呼び出し数に目を配る。文脈が膨らんだマネージャは止め、状態をファイルで引き継いで新しいマネージャに替える。

## 追跡

タスクごとに`.ccg/tasks/<task>/assignments.md`の1表で管理する（ccgのタスクディレクトリを使い、新しい管理資料は作らない）。

| ID | マネージャ | 実装担当 | 編集範囲 | 依存 | 状態 | Devinセッション | worktree |
| --- | --- | --- | --- | --- | --- | --- | --- |

状態は`planned` / `running` / `review` / `integrated` / `blocked` / `failed`のいずれか。
マネージャが自分の行を更新し、Opusはマネージャの行と契約を管理する。

## ログの多い作業はSWE-2が実行する

Claude系モデル（Opus・マネージャ）の使用量を抑えるため、ビルド、テスト（offline・live）、ログ調査、出力の長いBashはSWE-2が実行する。
Claude側は要約だけを読む。

- 検証もSWE-2のタスクに含める。完了報告に必ず次の要約を入れさせる（10行以内）: 件数（total/passed/failed/skipped）、失敗したテスト名と各1行の理由、skip理由の件数、所要時間。
- マネージャが読んでよいのは、その要約と`git diff --stat`まで。テストの生出力やログファイルは読まない。
- Claude側で実行してよいのは、出力の短い状態確認（`git status --short`、`git diff --stat`、`devin list`など）だけ。

## 検証の階層

| 階層 | 誰が | 何を | コマンド |
| --- | --- | --- | --- |
| 局所 | SWE-2 | 変更に直接関係するビルドとテスト | `dotnet build ResoLoop.slnx` / `dotnet test tests/RLoop.Tests/RLoop.Tests.csproj --no-build` |
| 統合 | マネージャが指示し、SWE-2が実行 | 担当機能を統合した後のオフライン全体 | `dotnet build ResoLoop.slnx` → `dotnet test ResoLoop.slnx --no-build` |
| live | Opusが決め、SWE-2が実行 | 全マネージャの統合後に1回 | `AGENTS.md`のopt-in手順（`RESOLOOP_RUN_INTEGRATION=1`、`Category=Integration`） |

- 同じコードを同じ環境で、担当が変わっただけで再実行しない。
- 共通基盤（`RLoop.Core`、`IResoniteClient`、CLI引数解析）の変更や影響範囲が不明な変更は、検証範囲を広げる。
- liveは共有のResoniteセッションを変えるので、同時に1本だけにする。実験は`ResoLoop_Test*` Slotの下だけで行い、正確なIDで片付ける。スキップされたテストを成功扱いせず、未検証として報告する。
- 未整備: live実行のラッパー（環境変数設定・排他ロック・実行記録`.test-runs/runs.jsonl`）はまだない。整備されるまで、liveの実行方法と対象はOpusがcharterで個別に指示する。

## SWE-2への指示に必ず入れるもの

上記の必須項目に加えて:

- 編集範囲（原則1ファイル。密結合の小さな変更はマネージャの判断でまとめてよい）。参照・調査は範囲外も可。
- 前提と契約（型・公開API・CLI引数・エラーコード）。全体設計を再発見させない。
- `AGENTS.md`の規則（依存方向、Resonite安全規則、上流を推測しない、CLI挙動を変えたらREADMEと`skills/codex/*`を同期）を守ること。
- ツールの制約: Devinが確認なしで実行できるのは`.devin/config.local.json`で許可した完全一致のコマンドだけ。それ以外のコマンド、Web、リポジトリ外の読み取りは、1回でも拒否されるとrun全体が止まる。
- 大きいファイルは複数回に分けて書く（1回の出力上限で打ち切られるため）。
