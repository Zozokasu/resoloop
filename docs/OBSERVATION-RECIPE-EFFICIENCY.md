# 観測の一括化とレシピ直接宣言の検証

2026-09-25。[前回測定](AUTHORING-EFFICIENCY.md)の改善後を今回の基準にし、追加改善を評価する。前回の元コミットとの比較ではない。

## 原因と今回の変更

前回は標準出力bytesが54.3%減った一方、CLIが58→85回、総トークンが6.9%増えた。改善後には個別の`component inspect`が25回あり、また適用前に5件のキー・parameterエラーが発生した。`schema describe`とprovider scaffoldは使われなかった。小さい出力だけでは往復数や宣言生成の手戻りを減らせていなかった。これはログに現れた手順差であり、各要因のトークン寄与率を分離した推定ではない。

今回実装したもの：

- `observe '$member:KEY.FIELD' [...] --state STATE`：最大64指定を1回で取得。同じComponentは呼出し内で重複取得せず、値・型・member ID・参照先IDを保持する。欠落指定は失敗。通常のstable参照解決を再利用し、再接続時の曖昧性拒否を維持する。
- `$recipe`直接宣言：export/includeやprototypeのコピー用helperを不要にし、`uix-<recipe>--<key>`で共有状態と操作部のキーを分離する。全必須引数・未知引数をまとめて検査する。形・色・素材・寸法・演出は追加しない。
- 子ノードの展開をscope確定後の1回に整理。入れ子やrepeatの未確定parameterを先に展開しない。既存prototypeのキーとinclude形式は保持する。
- build/uix/inspectスキルに、既知フィールドを確認フェーズごとにまとめる導線と、新規制作向け直接宣言を追加。

既存manifestのキーを自動移行しない。`$recipe`の接頭辞は従来のprototypeと違うため、適用済み宣言の置換は計画した移行が必要。`observe`は異なるComponentを同一瞬間に取得する保証を持たず、64指定の上限はlist/nested member内部のサイズ制限ではない。

## 機能検証

- オフラインテスト278件成功。追加検証：値・参照先の保持、重複読取の排除、0書込、欠落member/上限/誤selector拒否、再接続、同名の状態/操作部、caller visualの保持、必須/未知引数、入れ子/repeat。
- 更新したbuild/uix/inspectスキルのquick_validate成功。
- 実環境：Resonite 2026.9.18.82 / ResoniteLink 0.13.1.0。独立した`ResoLoop_Test_ObserveReplay_*`配下でReflection→diff→apply→比較→再apply→ID/name/parent検証→正確なroot削除→不在確認を実施。
- 実環境再applyは9 Slots / 9 Components unchanged、create/update/deleteは0。試験rootと状態値を他の制作runから分離。

## 解釈と残る負担

基準の個別`component inspect`は42＋27＝69回、新版は両方0回で、各5回の`observe`にまとめられた。新版は両方10個の直接レシピを使用した。対象を小さく読むだけでなく、既知の確認を同じ呼出しにまとめる導線が実際に選ばれた。総トークンは1組目・2組目とも減ったが、各2回の小標本であり、機能単体の因果効果や一般的な削減率を確定するものではない。

非キャッシュ入力の増加を隠して「使用量枠が19.4%減った」とは扱わない。例えば3回目のモデル呼出しは、基準1が入力35,205 / cache29,696、新1が入力35,788 / cache16,128。入力サイズが近くてもcache量に差があり、非cache差はこの呼出しだけで14,151。新2にも16,148、16,361の非cache入力を持つ呼出しがあった。数値は`request-usage.json`に保存した。キャッシュの揺れの原因を特定したわけではなく、補正値や仮想削減率は作らない。

最初のモデル入力は約28,800 tokensあり、その後は履歴が増える。したがってCLI返却bytesと総入力は比例しない。今回の往復削減は総入力に効いていると考えられるが、各要因の寄与率は分離していない。

手書きCanvas等のSlot/Componentキー衝突は全条件に残り、レシピ外の宣言を安全に生成する負担は消えていない。新1はPowerShellの`R` aliasによる不正な子要素とCanvasキー、 新2はCanvasキーの修正・再生成で手戻りが発生。基準1もalias/自動変数とキー衝突、基準2はURL指定漏れとCanvasキー修正で失敗した。レシピの名前分けは任意の手書き宣言や生成スクリプトの誤りを修復しない。

計測runnerがConsoleへ直接出力するため、PowerShell pipelineで結果を受けようとした基準1と新2に追加の手戻りがあった。新2は一度変更したtextをfinallyで復元してから再試行した。この計測環境の負担をCLI改善の効果と混同しない。次回の実験ではrunnerのpipeline対応を事前検証するのが望ましいが、今回は開始後に条件を変更せず、失敗を含む全量を残した。
